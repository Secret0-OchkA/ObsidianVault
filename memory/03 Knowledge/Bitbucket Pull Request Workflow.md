# Bitbucket Pull Request Workflow

Эта заметка описывает порядок подготовки и оформления Pull Request в Bitbucket Cloud для Dev Orchestrator. Это reusable workflow; сведения о конкретном репозитории, ветках, командах и Jira-задачах остаются в репозитории и в текущем запросе пользователя.

## Когда использовать

Используй workflow, когда пользователь явно просит создать Pull Request, оформить PR или отправить изменения на ревью. Самостоятельно не создавай PR, не назначай reviewers и не выполняй merge только потому, что ветка уже запушена.

Перед началом уточни только действительно неизвестное:

- исходную ветку;
- целевую ветку;
- Jira/task ID, если он не следует из имени ветки;
- reviewers или assignee, если пользователь ожидает их назначения.

Не угадывай assignee или reviewers. Если назначение не указано, оставь поле пустым или попроси пользователя выбрать получателей.

## Подготовка

1. Проверь текущую ветку и remote.
2. Убедись, что исходная ветка опубликована в remote и содержит нужный commit.
3. Проверь рабочее дерево. Незакоммиченные изменения должны быть явно согласованы с пользователем; не включай их в PR молча.
4. Проверь отсутствие незакрытого merge/rebase и конфликтных маркеров.
5. Выполни минимальный review изменённого scope.
6. Запусти релевантные build, tests, lint или runtime checks.
7. Зафиксируй точные результаты: количество passed/failed/skipped, имя упавшего теста, а также `stopped`, `timed out` или `not run`, если применимо.

Для .NET по умолчанию ориентируйся на repository instructions и цикл `Coder -> Review -> Tests -> Done`. Focused check не заменяет полный relevant suite, если пользователь не ограничил scope.

## Создание PR в Bitbucket

1. После push используй ссылку на PR, которую вывел remote, если она есть.
2. Иначе открой Bitbucket для нужного repository и выбери `Create pull request`.
3. Укажи:
   - `Source`: исходная feature/task ветка;
   - `Destination`: целевая ветка, обычно `dev` или ветка, названная пользователем;
   - заголовок PR;
   - описание PR;
   - reviewers и assignee только по согласованному списку.
4. Проверь, что Bitbucket показывает ожидаемый commit range и не сообщает о merge conflicts.
5. Создай PR только после проверки полей.
6. После создания верни пользователю URL PR, source/destination branches и commit, вошедший в PR.

Если доступен автоматизированный Bitbucket/API-инструмент, используй его только с известными параметрами и безопасным способом аутентификации. Не записывай tokens, passwords или credential values в заметку, описание PR, логи или команды.

## Заголовок PR

Предпочтительный формат:

`[TASK-ID] Краткое действие над областью изменения`

Примеры:

- `[PDF-66] Обновить ветку PDF-66 относительно dev`
- `[TASK-123] Добавить обработку отмены операции`

Если task ID отсутствует, используй короткий заголовок с глаголом и объектом изменения. Не помещай в заголовок список файлов, детали реализации или результаты тестов.

## Описание PR

Используй компактную структуру, по которой reviewer может быстро проверить цель и доказательства:

```markdown
## Что изменено
- Кратко перечислить поведенческие изменения.
- Указать важные решения по конфликтам или совместимости.

## Область изменений
- Модули, endpoints, очереди, конфигурация или тесты, которых касается PR.

## Проверка
- `dotnet build ...` — passed/failed.
- `dotnet test ...` — N passed, M failed, K skipped.
- Дополнительные проверки — результат.

## Риски и ограничения
- Известные риски, внешние зависимости и незапущенные проверки.
- Если suite остановлен или недоступен, написать это явно.

## Связанные задачи
- TASK-ID или ссылка на Jira, если она известна.
```

Не превращай описание в журнал команд. Оставляй только сведения, которые помогают принять решение по ревью: цель, заметные изменения, validation evidence, риски и связанные задачи.

## Перед передачей PR на ревью

Проверь:

- PR создан из правильной ветки в правильную целевую ветку;
- заголовок соответствует task ID и описывает цель;
- описание содержит фактические результаты проверок;
- reviewers и assignee указаны только по согласованию;
- нет секретов, сырых payloads или credential values;
- рабочее дерево после создания PR осталось в ожидаемом состоянии;
- merge PR не выполнялся, если пользователь просил только создать или оформить PR.

## Отчёт пользователю

Сообщи кратко:

- что PR создан;
- URL PR;
- source -> destination;
- commit или диапазон commits;
- какие проверки прошли;
- какие проверки failed, stopped, timed out или не запускались;
- открытые вопросы и остаточные риски.

Не называй PR готовым к merge, если обязательная проверка не запускалась или завершилась неуспешно.
