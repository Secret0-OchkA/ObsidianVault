# Jira Task Authoring

## Назначение

Превращать проанализированное требование в корректно оформленную Jira-задачу с полями `Description`, `As Is`, `To Be`, `Steps to Test` и флажком `DoR` (Definition of Ready). Если требование содержит несколько независимо поставляемых частей, создавать несколько связанных задач вместо одной перегруженной.

## Проектные исключения

Эта инструкция является общим fallback-процессом: схему Jira нужно получать через metadata-вызовы, потому что IDs полей отличаются между сайтами и проектами.

Для проекта `ADOC` использовать [[03 Knowledge/Jira Ticket Creator ADOC|специальную инструкцию ADOC]] с подтвержденными IDs полей, ADF-форматом, значениями опций и переходами. Для ADOC пропустить общий discovery-процесс и следовать специальной инструкции.

Если для другого проекта появится подтвержденная карта полей, вынести ее в отдельную проектную инструкцию по аналогии с ADOC, а не хардкодить IDs в общей инструкции.

## Разбиение задач

- Самостоятельная задача должна оставлять проект в состоянии, где код компилируется или собирается после ее выполнения, даже если новая часть еще не подключена end-to-end.
- Разбивать требование на несколько задач, если части независимо тестируются, имеют естественную build-clean границу или не обязаны поставляться атомарно.
- Оставлять одну задачу, если части нельзя отдельно собрать или проверить, например изменение сигнатуры вместе со всеми обязательными call sites.
- При разбиении применять все правила полей к каждой задаче отдельно. Каждая задача должна быть понятна без чтения соседней.
- Связывать разделенные задачи через `createIssueLink` и сохранять порядок зависимостей.

## Язык

Поля Jira `Description`, `As Is`, `To Be` и `Steps to Test` заполнять на английском независимо от языка исходного требования. Отчет пользователю составлять на языке пользователя.

## Обязательные правила полей

- **Assignee** - если исполнитель не указан, сначала спросить пользователя, на кого назначить задачу, и дождаться ответа. Не угадывать исполнителя и не создавать задачу без assignee без явного подтверждения пользователя.
- **Description** — формулировка проблемы: цель, контекст и важность. Не добавлять детали реализации, имена классов, файлов или методов.
- **As Is** — текущее поведение или состояние. Для новой возможности использовать `N/A — new capability`.
- **To Be** — конкретное и однозначное целевое поведение после изменения. Это поле определяет готовность задачи.
- **Steps to Test** — нумерованный воспроизводимый список для проверки задачи после реализации. Каждый шаг содержит действие и ожидаемый результат. Не писать только «проверить, что работает».
- **DoR** — устанавливать флажок только если `To Be` полностью заполнено и однозначно. Если поле пустое или содержит открытые вопросы, оставить DoR выключенным и указать причину.

## Процедура

0. Подтвердить исполнителя. Если пользователь не указал assignee, спросить, на кого назначить задачу, и дождаться ответа до создания задачи. Jira account ID искать только после указания человека.
1. Определить Jira-проект и тип задачи. Если проект неизвестен или неоднозначен, вызвать `getVisibleJiraProjects` и подтвердить выбор с пользователем.
2. Для выбранного проекта и типа задачи вызвать `getJiraProjectIssueTypesMetadata` и `getJiraIssueTypeMetaWithFields`.
3. Найти поля по смыслу, а не только по точному имени: `As-Is` / `Current Behavior`, `To-Be` / `Target Behavior`, `Steps to Reproduce/Test`, `DoR` / `Ready`.
4. Составить Description на 2–4 предложения без деталей реализации.
5. Составить As Is: текущее состояние или `N/A` для greenfield-задачи.
6. Составить To Be. Если требование не позволяет сформулировать его однозначно, задать пользователю один уточняющий вопрос вместо предположений.
7. Составить 3–8 шагов тестирования, каждый с действием и ожидаемым результатом.
8. Установить DoR по правилу выше.
9. Заполнить остальные поля только если они обязательны по metadata или явно заданы пользователем. Не придумывать значения необязательных полей.
10. Создать или обновить задачу через `createJiraIssue` / `editJiraIssue` только после подтверждения assignee.
11. Если задач несколько, связать их через `createIssueLink`.
12. Вернуть пользователю ключ и ссылку задачи, кратко перечислить заполненные поля, сообщить assignee и состояние DoR. Если DoR выключен, назвать недостающую информацию.

## Антипаттерны

- Не угадывать IDs custom fields: сначала получать metadata текущего проекта и типа задачи.
- Не устанавливать DoR «на всякий случай».
- Не добавлять в Description и To Be детали реализации: файлы, классы и методы относятся к этапу разработки.
- Не пропускать обязательные поля, найденные в metadata.
- Не объединять независимые части только ради создания одной задачи.
- Не разделять части, которые нельзя собрать или проверить независимо.
